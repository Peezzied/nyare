# Feature Specification: Dev Audit Trace Console

**Feature Branch**: `010-audit-trace-console`

**Created**: 2026-10-20

**Status**: Draft

**Input**: User description: "in nyare.dev, i want to integrate a nyare themed web page where i can decently see the ai audits from the console while also navigate the database therein as well. it's not a normal database explorer. that explorer follows the reference stubs generated by the audit and back trace it to the actual database object."

## Clarifications

### Session 2026-10-24

- Q: How should the console categorize and represent the start and end of an AI processing run in the audit feed? → A: Single `LIFECYCLE` category with start (run ID, pending note count) and end (elapsed time, item counts, status).
- Q: Should the dashboard capture and display errors? → A: Yes, capture and display planning errors and unhandled exceptions with ERROR severity, cause details, affected record references, and dedicated error filtering.
- Q: What scope and origin details should the audit trace dashboard capture for incoming requests? → A: Audit user ID, username, and trigger type on AI planning and async jobs, with extensible origin metadata on all audit events.
- Q: Which CRUD operations should the dashboard capture in the audit feed? → A: Option A - Audit mutating actions (Create, Update, Delete, Archive) across core entities with user origin, operation type, and target entity ID.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Trace an audit entry to the record it describes (Priority: P1)

A developer runs a planning pass, watches the audit lines scroll by, and wants to know which stored record a line refers to. They open the developer console, select the audit line, and immediately see the record the planner acted on together with the fields the audit cited.

**Why this priority**: This is the core value. Without a correct pointer from audit to record, the console is just a prettier log viewer.

**Independent Test**: Emit one audit of each category during a planning run, then select each entry in the console and confirm it resolves to the expected stored record.

**Acceptance Scenarios**:

1. **Given** a task-promotion audit that names a task, **When** the developer selects it, **Then** the console shows that exact task record with its title, owning course, scheduling state, and duration.
2. **Given** a task-planning audit that names only a source note and a title, **When** the developer selects it, **Then** the console shows the source note and marks the matching task as inferred rather than exact.
3. **Given** an event-planning audit, **When** the developer selects it, **Then** the console shows the source note and the stored deadline record it produced, marked as inferred when matched by title.
4. **Given** an image-context audit, **When** the developer selects it, **Then** the console shows both the image record and the note that owned it during the run.
5. **Given** an unrelated-info audit, **When** the developer selects it, **Then** the console shows the source note and highlights the quoted unrelated text inside it.
6. **Given** a lifecycle audit, **When** the developer selects it, **Then** the console shows the run identifier, execution status, elapsed processing duration, and links to the batch of source notes evaluated during the run.
7. **Given** an audit entry or lifecycle run, **When** the developer selects it, **Then** the console shows the initiating user ID, username, and trigger origin.
8. **Given** a data mutation audit, **When** the developer selects it, **Then** the console shows action type, user, and navigates to the target record.

---

### User Story 2 - Walk the database through references (Priority: P2)

From a traced record, the developer follows its relationships to inspect neighbouring data: the owning course, sibling tasks, source notes, attached images, and context facts. This replaces a table browser with a relationship walk that starts at an audit.

**Why this priority**: This is the "navigate the database" half of the request. It makes the console useful for verifying the full effect of a planning run, not just one row.

**Independent Test**: Start at one note, reach its course, then its sibling tasks and events, and return to the originating audit without using a table list.

**Acceptance Scenarios**:

1. **Given** a note is displayed, **When** the developer opens its relations, **Then** the console lists the owning course, tasks, events, and context facts linked to that note, plus images referenced in its content.
2. **Given** an image is displayed, **When** the developer opens its relations, **Then** the console lists every note whose content references that image.
3. **Given** a task or event is displayed, **When** the developer opens its relations, **Then** the console lists the owning course and the source note.
4. **Given** a course is displayed, **When** the developer opens its relations, **Then** the console lists its schedules, notes, tasks, events, and context facts with total counts.
5. **Given** no audit is selected, **When** the developer picks a course from the console's entry list, **Then** the same relationship walk starts from that course.

---

### User Story 3 - Read the live audit feed (Priority: P3)

The developer watches audits arrive while a planning run executes, filters to one category, and pauses the feed to read a long rationale without the list moving.

**Why this priority**: Convenience for live debugging. The trace remains usable from retained history if live refresh is unavailable.

**Independent Test**: Trigger a planning run while the console is open and confirm new entries appear without a page reload, filtering isolates one category, and pause stops movement.

**Acceptance Scenarios**:

1. **Given** the console is open, **When** a planning run emits audits, **Then** new entries appear at the top of the feed without a manual refresh.
2. **Given** several categories are present, **When** the developer selects one category filter, **Then** only entries of that category remain visible.
3. **Given** the feed is live, **When** the developer pauses it, **Then** the list stops updating and the pause state is visible.
4. **Given** the developer resumes a paused feed, **When** the feed refreshes, **Then** entries emitted during the pause appear.
5. **Given** more entries exist than the retention limit, **When** the console loads, **Then** only the most recent retained entries are shown.

---

### User Story 4 - Inspect processing errors and system exceptions (Priority: P2)

When an AI planning pass fails, the developer sees the error in the dashboard feed. The developer selects the error and inspects the message, cause summary, and affected context without reading raw terminal logs.

**Why this priority**: When planning fails, developers need immediate visibility into what failed, why, and which records were affected.

**Independent Test**: Trigger a failing planning pass, confirm an error event appears, and verify the console displays the error details and related record references.

**Acceptance Scenarios**:

1. **Given** an AI planning run fails, **When** the error occurs, **Then** the console captures an entry with `ERROR` severity showing the message and run identifier.
2. **Given** `ERROR` entries exist, **When** the developer selects the error filter, **Then** only error entries remain visible.
3. **Given** an error entry is displayed, **When** the developer selects it, **Then** the console shows the exception type, message, root cause, and affected notes.
4. **Given** an error occurs during database access, **When** the developer inspects records, **Then** the console displays an isolated card error state without crashing.

---

### Edge Cases

- An unhandled exception occurs mid-run: the console logs an ERROR lifecycle event with exception details, marks the run as failed, and retains prior audit entries intact.
- An error message contains an extensive stack trace: the console shows a concise summary with an expandable full-text preview.

- A referenced record was deleted after the audit was emitted: the console shows an explicit "record no longer exists" state for that reference instead of an empty card.
- A deleted record is traced from a DELETE mutation audit: the console shows the tombstone state with deletion timestamp and initiating user.
- An audit names a reference that never resolved to a stored record: the console shows the raw reference value and states that no record matched.
- The audit feed is empty because no planning run has occurred since start-up: the console shows an empty-state message and still offers the course entry point.
- A malformed or truncated audit line is received: the console shows the verbatim text and no resolved references, without failing the rest of the feed.
- A note's content has no image references: the image relation is shown as empty, not as an error.
- A relation group holds more records than the display limit: the console shows the first records in a stable order and states the total count.
- An image record is displayed: its binary content is never shown or transferred to the console.
- The database is unavailable while the console is open: the console reports the failure per panel and keeps the audit feed readable.
- A planning run is active while the developer navigates: newly emitted entries do not disturb the record currently being inspected.
- The developer reloads the page: retained audits remain available for the session, and prior traces are not persisted.
- An audit message contains quoted text with separators or newlines: the console still identifies its categories and references.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The console MUST be available only in the development environment and MUST NOT be reachable or included in a production deployment.
- **FR-002**: The console MUST present planning audit events captured from the running service, newest first.
- **FR-003**: The console MUST retain the most recent 500 audit events for the process lifetime and discard older events.
- **FR-004**: Each audit entry MUST show its category, timestamp, severity (including INFO, WARN, and ERROR), and the verbatim audit message.
- **FR-005**: The console MUST let the developer filter entries by category across all seven categories: lifecycle, task planning, task promotion, event planning, image context, unrelated information, and data mutation.
- **FR-006**: The console MUST let the developer pause and resume feed updates, and MUST show the current pause state.
- **FR-007**: Selecting an audit entry MUST resolve every entity reference it contains to a stored record.
- **FR-008**: The console MUST distinguish references that are exact (the audit names the record identifier) from references that are inferred (matched by title within the source note).
- **FR-009**: For each resolved record, the console MUST show enough identity fields to recognise it: title or name, owning course, relevant dates, and status where applicable.
- **FR-010**: The console MUST let the developer navigate from any displayed record to its directly related records.
- **FR-011**: The console MUST resolve these relations: note to owning course, note to its tasks, events, and context facts, note to images referenced in its content, image to referencing notes, and task, event, or context to owning course and source note.
- **FR-012**: The console MUST provide a course list as an alternate entry point when no audit is selected.
- **FR-013**: The console MUST limit each relation group to 50 displayed records and MUST state the total number available.
- **FR-014**: The console MUST never display or transfer an image's binary content.
- **FR-015**: The console MUST be strictly read-only and MUST NOT create, update, or delete any stored data.
- **FR-016**: The console MUST show an explicit "record no longer exists" state when a referenced record cannot be found.
- **FR-017**: For unrelated-information audits, the console MUST locate and highlight the quoted text inside the source note content when that text is present.
- **FR-018**: The console MUST show the trail from the originating audit to the record currently displayed, and MUST let the developer return to any earlier step in that trail.
- **FR-019**: The console MUST display the reference value of every resolved record, so it can be compared with the audit message.
- **FR-020**: The console MUST apply the Nyare visual identity: warm parchment surfaces, ocean cyan primary accent, slate body text, and the product's display and body typefaces.
- **FR-021**: The console MUST capture AI processing lifecycle events: a start event (run identifier, timestamp, and target note identifiers) and an end event (run identifier, timestamp, elapsed duration in milliseconds, extracted entity counts, and execution status: completed, failed, or cancelled).
- **FR-022**: The console MUST capture and display planning errors and unhandled exceptions, recording timestamp, error message, exception type, and root cause snippet.
- **FR-023**: The console MUST provide a filter allowing developers to isolate `ERROR` entries in the feed.
- **FR-024**: The console MUST capture and display request origin metadata for each audited run and event, recording initiating user ID, username or display label, and trigger source (such as WEB_SESSION or SYSTEM_JOB).
- **FR-025**: The console MUST capture data mutations (Create, Update, Delete, Archive) on core entities, recording user ID, username, action, entity kind, identifier, and summary.

### Key Entities *(include if data involved)*

- **Audit Event**: One line emitted by the planner or service layer during an operation. Holds a category (lifecycle, task planning, task promotion, event planning, image context, unrelated information, or data mutation), timestamp, severity, the verbatim message, request origin metadata, and the entity references extracted from it.
- **Mutation Audit**: A data mutation audit capturing entity creation, updates, deletion, or archival, recording action type (`CREATE`, `UPDATE`, `DELETE`, `ARCHIVE`), target entity kind, identifier, initiating user, and summary.
- **Request Origin**: Contextual metadata identifying the initiating actor and trigger source, including user ID, username, and trigger type (such as WEB_SESSION or SYSTEM_JOB).
- **Error Diagnostic**: Diagnostic details associated with a failed run or error event, including exception type, error message, root cause snippet, and affected run or record identifiers.
- **Lifecycle Run**: An AI processing execution bounded by a start and end event, carrying a unique run identifier, initiating user ID, username, trigger source, execution status, elapsed milliseconds, and target note references.
- **Audit Reference**: A pointer found inside an audit event. Holds the referenced kind (note, task, event, image, course, context, schedule), the reference value, and whether the match is exact or inferred.
- **Trace Node**: A stored record presented by the console. Holds its kind, identifier, identity fields, and its relation groups.
- **Relation Group**: A labelled set of trace nodes reachable from one trace node, with an displayed count and a total count.
- **Course**: The root container that owns notes, schedules, tasks, events, and context facts. Serves as the alternate entry point for browsing.
- **Image**: A stored attachment identified by content type, filename, size, and generated description, referenced from note content by its identifier.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A developer reaches the stored record behind any audit entry in at most two interactions and within five seconds of selecting the entry.
- **SC-002**: All seven audit categories are represented in the console and traceable, with zero categories missing.
- **SC-003**: Zero silent omissions: every reference named by a selected audit resolves either to a record or to an explicit not-found state.
- **SC-004**: A developer reaches any record related to a course in at most three navigations from the course entry point.
- **SC-005**: The console adds no more than one percent to a planning run's duration compared with a run where the console is not loaded.
- **SC-006**: The production artifact contains zero console pages, endpoints, and supporting components.
- **SC-007**: The audit feed renders and remains interactive with the full retention limit of 500 entries in under one second.
- **SC-008**: No console interaction changes stored data, verified by comparing record counts and modification timestamps before and after a full walkthrough.
- **SC-009**: A developer can inspect the exception type and root cause of any failed planning run within two interactions from the feed.

## Out of Scope

- Arbitrary query execution, schema editing, or write access of any kind.
- Persisting audit history across restarts, sharing it between developers, or exporting it.
- Showing the untruncated planner prompt or raw model response.
- Reconstructing the state of a record as it was at audit time.
- Authentication beyond the existing development environment.
- Replacing the application's normal user-facing views.

## Assumptions

- The console is developer tooling that belongs to the development environment only, consistent with the constitution's separation of development rules from presentation components.
- Audit messages already contain the resolved record identifiers needed for exact tracing, so the planner's logging behaviour does not change.
- Although local development uses seeded accounts, request origin metadata records the active session user identifier, username, and trigger source on all audited runs.
- Retained audits live in memory and reset when the service restarts. A 500-entry limit keeps memory bounded.
- Inferred matching is limited to title comparison within the source note and is always labelled as inferred.
- Image ownership is derived from references inside note content, because images carry no stored owner.
- Records are shown in their current state, not their state at the time of the audit.
- The console reuses the existing development data set and requires no separate seed data.
