# Nyare Conceptual Model & Domain Dictionary

Nyare is a **calendar-first academic planning assistant**. It transforms course-linked student journal notes into structured academic intelligence, providing flexible, high-level task recommendations anchored by rigid academic constraints.

---

## 1. Core Concept & Pipeline

The system operates along a clear, unidirectional information flow:

```text
Course Schedule
      ↓
Course-linked Journal Entry
      ↓
AI Processing & Planning (combined trigger for today's notes)
      ↓
Tasks / Academic Events / Academic Context
      ↓
Study Plan & Scheduling (updates scheduledDate and duration)
      ↓
Calendar View (main interface)
```

---

## 2. Core Entities & Hierarchy

```text
Academic Term (Conceptual Grouping)
└── Course (Organizational Root)
    ├── Class Schedules (Recurring weekly meeting times)
    ├── Journal Entries / Notes (Source text)
    ├── Tasks (Actionable items to do)
    ├── Academic Events / Deadlines (Fixed occurrences & constraints)
    └── Academic Context (Descriptive facts & planning context)
```

### Entity Definitions

### `Academic Term`
* **Definition**: The conceptual period (semester, trimester, quarter) spanning academic courses.
* **Role**: Provides the overarching academic timeframe. In the initial MVP, `Course` serves as the primary operational and persistence container.

### `Course`
* **Definition**: A distinct academic subject or class in which a student is enrolled.
* **Role**: The central anchor for all student data. Every journal entry, task, event, schedule, and context item belongs to exactly one course.

### `Schedule`
* **Definition**: Recurring weekly class meeting times (`dayOfWeek`, `startTime`, `endTime`).
* **Role**: Anchors the calendar view, providing context for when classes take place and serving as quick navigation points for writing journal notes.

### `Journal Entry` (`Note`)
* **Definition**: The raw, student-authored text or notes written during or after class, stored in rich JSON format.
* **Role**: The **immutable source of truth**. AI processes journal entries to extract structured entities.

### `Task`
* **Definition**: An actionable academic work item that the student needs to complete (e.g., *"Finish research proposal"*, *"Read Chapter 4"*).
* **Attributes**: Title, description, origin (`STUDENT_EXTRACTED`, `AI_GENERATED`, `MANUAL`), status (`TODO`, `IN_PROGRESS`, `COMPLETED`), optional estimated duration, and optional flexible recommended date (`scheduledDate`).
* **Origin Types**:
  - `STUDENT_EXTRACTED`: Action items extracted directly from student journal notes.
  - `AI_GENERATED`: Study preparation tasks generated by the AI planner for upcoming academic events within a 14-day window.
  - `MANUAL`: Tasks created directly by the student in the UI or API.

### `Academic Event`
* **Definition**: Something that happens or is expected to happen at a specific date or time. Academic events represent **rigid academic constraints**.
* **Taxonomy**:
  ```text
  Academic Event
  ├── Exam (Formal summative assessment)
  ├── Quiz (Short assessment)
  ├── Presentation (Oral or project demonstration)
  ├── Class Activity (In-class exercise or lab)
  └── Deadline (Latest required time for submission/completion)
  ```

### `Academic Context`
* **Definition**: Temporal, descriptive facts about the student's academic situation that assist AI in understanding and planning, but are not themselves actions or scheduled events.
* **Examples**:
  - *"The exam covers Chapters 1–4."* (Scope)
  - *"The proposal must include introduction and methodology."* (Requirement)
  - *"The student has not started the proposal."* (Current progress)
  - *"Chapter 5 has not yet been discussed in class."* (Dependency / pacing)
* **Temporal Nature**: Academic context is time-aware; older context may degrade in relevance as new information emerges or progress is made.

### `Study Plan`
* **Definition**: A virtual, presentation-layer grouping of tasks recommended for execution, dynamically generated by the AI Planner.
* **Persistence Boundary**: **The Study Plan is NOT a separate database entity.** It is a computed view returned to the UI.
* **Tri-State Recommendation Structure**:
  1. **Scheduled**: Recommended for a specific calendar date (`scheduledDate != null`).
  2. **Later**: Recommended for action without a specific target date (`scheduledDate == null && duration != null`).
  3. **Backlog**: Actionable, but lacks sufficient context or detail for confident scheduling (`scheduledDate == null && duration == null`).

## 3. Important Domain Distinctions

### 1. Academic Event vs. Deadline
* **Distinction**: A **Deadline** is a specific subtype of **Academic Event**.
* **Rationale**: An Academic Event is any time-anchored occurrence (exam, quiz, presentation, class activity). A deadline specifically denotes the latest permissible moment to submit or conclude work. Both impose rigid external constraints on planning.

### 2. Task vs. Academic Event
* **Distinction**: A **Task** is an action the student does. An **Academic Event** is an occurrence that happens.
* **Independence**: Neither strictly requires the other. A task can exist without a deadline (e.g., *"Review algebra notes"*), and an event can exist without an associated task (e.g., *"Guest lecture on Friday"*).

### 3. Academic Context vs. Task
* **Distinction**: A **Task** is an action to perform. **Academic Context** provides the background information that shapes or guides how that action is planned.
* **Example**:
  - *Task*: *"Review Chapter 4"*
  - *Academic Context*: *"Exam covers Chapters 1–4; student has not reviewed Chapter 4."*

### 4. Academic Context vs. Academic Event
* **Distinction**: An **Academic Event** occurs at a defined date/time. **Academic Context** describes state, coverage, scope, difficulty, or progress.
* **Example**:
  - *Academic Event*: *"Math exam on Friday"*
  - *Academic Context*: *"Exam covers Chapters 1–4"*

### 5. Recommended Date vs. Deadline
* **Distinction**: A **Deadline** is a rigid academic constraint. A **Recommended Date** is an AI-suggested date for working on a task.
* **Flexibility**: If a student misses a recommended date, no external rule is broken; the plan simply adapts. Missing a deadline violates an academic constraint.

### 6. Extractability vs. Plannability
* **Distinction**: 
  - **Extractability**: Can Nyare extract a meaningful academic entity from what the student wrote?
  - **Plannability**: Is there enough context to make a confident recommendation on when/how to do it?
* **Uncertainty Rule**: If a task is extractable but not plannable (e.g., *"I have to work on my project"* with no deadline or duration), it is preserved as **Backlog** or **Later**, never forced onto a calendar date through fabricated information.

### 7. Source Information vs. Extracted Information (Materialization)
* **Distinction**: The journal entry is the **Source Information** (unmodified student notes). Extracted Tasks, Events, and Context are the **Extracted Information** (structured entities materialized into application state).
* **Materialization**: Saving extracted information into database tables is standard application behavior, not an autonomous reconciliation engine.

### 8. Task Consideration vs. Task Updating
* **Distinction**:
  - **Task Consideration**: Existing tasks inform subsequent AI planning runs.
  - **Task Updating**: Mutating existing task records based on new information.
* **MVP Boundary**: The system does NOT automatically rewrite, split, or merge student task titles or descriptions. However, the AI planner CAN update scheduling fields (`scheduledDate` and `duration`) on existing open tasks, and promotes `BACKLOG` tasks when new academic context enables planning.

## 4. Preserving Uncertainty & Grounded Duration Estimation

A foundational tenet of Nyare is that **missing information must remain uncertain unless grounded**:
1. **Never Invent Data**: The AI must never invent deadlines, dates, or priority metrics.
2. **Three Information States**:
   - **Known**: Stated explicitly in notes or syllabus (e.g., *"Exam is on Nov 12"*, *"Allot 45 mins"*).
   - **Inferred / Estimated**: Reasonably deduced without arbitrary guessing:
     - Date anchors resolved from recurring schedules and deadlines.
     - Commonsense baseline duration for standard setup tasks (e.g., IDE or software installation).
     - Context-backed rough duration for study and review tasks based on topic scope or student struggles.
   - **Unknown**: Absent and ungrounded (e.g., unspecified deadline, abstract task with zero context -> `duration = null`).
3. **Graceful Handling**: Unknown properties remain null or unassigned. Tasks with high uncertainty are categorized under **Backlog** or **Later**.
